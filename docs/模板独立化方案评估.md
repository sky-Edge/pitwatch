# 模板独立化方案评估

## 从「模板挂在项目下」改为「模板声明它适用于哪些项目」

> 背景：用户提出「每个项目单独维护一个模板太繁琐了，能否把模板从项目中独立提取出来，改由模板来定义其作用于哪个项目？」  
> 评估日期：2026-10-08　｜　评估方式：只读副本库 + 真实模板数据逐条核对，未改动任何生产数据

---

## 一、结论先行

| 问题        | 结论                                                                        |
| --------- | ------------------------------------------------------------------------- |
| 可行吗       | **可行**。数据模型与导出路径其实已经具备了「独立模板」的骨架                                          |
| 能省多少事     | 你现有 **18 份自定义模板**，其中 **15 份是同一个版式族**（基坑日报）反复上传 → 可收敛到 **1 份通用 + 2 份专用**   |
| 最大收益      | 改一次表头/加一列，**只改 1 份**，不用 12 个项目各改一遍                                        |
| 最大前提      | 上一轮做的「母版里的旧基坑名自动换成本项目名」**必须先在**。没有它，共用模板会让所有项目都印成同一个基坑名                   |
| 但不能「一份通吃」 | 你的项目里有 **3 套点号体系**（`JJC1~12` / `QC01~09` / 中文点名），跨族共用会串点号                 |
| 代价        | 后端 4 个文件 + 前端 3 个文件 + 迁移 1 处 + 测试 1 新 4 改；**新列必须手写 ALTER**（本项目没有 Alembic） |
| 风险等级      | 总体**低**。不动原始数据、不搬文件，最坏情况只需忽略新增的表和列即可回退                                    |

**一句话**：技术上完全可行，真正需要你拍板的不是"能不能做"，而是**共用模板后，母版里那些固定文字（结论段、概况）怎么办** —— 那是这次改造唯一解决不了的硬骨头。

| - | ----- | ------------------------------------------------------ | ---------------------------------------------------------------- |

| 2 | 上传    | 必须先有项目：`POST /projects/{pid}/export-templates/upload`  | `backend/api/v1/export_templates.py:42`                          |

| 4 | 文件落盘  | 存进 `templates/{project_id}/xxxx.xlsx`                  | `export_template_service.py:202`、`api/v1/export_templates.py:59` |
| 5 | 改名/删除 | 按 `project_id` 做归属校验                                   | `export_template_service.py:245,273`                             |

## 三、关键取证：模板里到底有多少「项目私有物」

这决定了**能共用到什么程度**。把模板学到的 `layout_json` 逐字段拆开看：

| 模板内含的东西                              | 是否项目私有   | 现状                                                 |
| ------------------------------------ | -------- | -------------------------------------------------- |
| 列号映射（点号/初始值/累计/速率…）、`data_start_row` | **完全无关** | ✅ 可共用                                              |
| 封面日期格、期次格、签字格、天气格                    | **完全无关** | ✅ 可共用                                              |
| 工程名称文字                               | 私有       | ✅ **已解决** —— 导出时按项目名整体替换（上一轮 `_sync_project_name`） |
| 测点**行数**                             | 私有       | ✅ **已解决** —— 点数多于母版时自动补行 + 原始数据区自动补块               |
| 原始数据区的**点号标签**                       | 私有       | ⚠️ **未解决**（见下）                                     |
| 概况/分析/结论段的**固定文字**                   | 私有       | ❌ **未解决**（且本来就有问题）                                 |

### 未解决项 1：原始数据区的点号标签会残留

原始数据区的槽位是**模板学到的 `point_no → 起始行` 映射**（`t19` 学了 `JJC1…JJC12`）。但填充时只写**坐标值列**，不重写点号标签：

```python
# backend/reports/master_report.py:508-516
for side, entry in blocks:
    pno = entry["point_no"]
    data = by_point.get(pno, {})        # 项目里没有这个点号 → {}
    _set_num(ws, start_row + 0, col, ...)   # 只写值列，点号格不动
```

**后果**：拿一份 12 点的模板（t12/t19/t20 都是 12 点）去导 10 点的项目 11、12，报表右下角会**印出 `JJC11`、`JJC12` 两个点号、但坐标是空的**；拿 8 点的模板（t15）去导 12 点的项目 8，则是 4 个点整块缺失（这就是你上次截图报的"这个没有跟上"）。

→ **共用模板之前必须先补这一条**：写坐标值时顺手把点号列重写为本项目的点号、多余槽位连标签一起清空。

### 未解决项 2：固定文字仍是"别人的基坑"

母版的概况段、分析段、结论段是**从别的基坑那期报表另存**来的，里面写着别的基坑名（已能替换）、以及别的实测结论（替换不了）。项目待办里已记着"母版「分析」sheet 的 12 段结论来自别的基坑"。

- **现在**：一份模板只服务一个项目，改一句结论只影响自己 —— 问题被"模板按项目隔离"掩盖着
- **共用后**：一份模板服务 9 个项目，这个矛盾会**立刻放大**

→ 这是本次改造**唯一无法靠代码解决的问题**，需要你选一条路（见第九节问题 2）。

## 四、关联方式怎么改：三个候选

### 方案 A（推荐）：模板 ↔ 项目 多对多 + 「通用」开关

```
export_templates            新增 is_global(bool)
template_projects           新增关联表 (template_id, project_id) 联合主键
```

- 模板可勾选 **N 个项目**，也可置为 **通用**（所有项目可见）
- 「通用」用**显式布尔**表达，而不是"绑了 0 个项目"—— 后者有歧义（是还没配？还是故意通用？）
- 表达力最全：既能"这一份给这 3 个项目用"，也能"这一份谁都能用"

### 方案 B：按「版式族 / 类别」分组

给模板加 `category`（基坑日报 / 钢栈桥 / 路基），项目选类别 → 该类模板自动可用。

- 模板数量涨到几十份、类别稳定时很舒服
- **但你现在只有 3 个族** —— 引入类别层属于多余的抽象，且"哪个项目属于哪个类别"还是要配一遍，没省掉配置动作

### 方案 C：不改表，只加「复制到其他项目」

一键把模板复制到多个项目。

- 改动最小（一天能做完）
- **但治标不治本**：产生 N 份副本，以后仍要各自维护 —— 你要的是"**改一次全局生效**"，不是"传一次省点手"

### 对比

|                | 改动量 | 表达力 | 改一次全局生效 | 风险 |
| -------------- | --- | --- | ------- | -- |
| **A 多对多 + 通用** | 中   | 高   | ✅       | 低  |
| B 按类别分组        | 中   | 中   | ✅       | 低  |
| C 复制到多项目       | 小   | 低   | ❌       | 极低 |

**推荐 A**。理由：只有 A 同时满足「改一次全局生效」和「个别项目单独绑」两个诉求，且改动量在一次正常迭代的量级内。

## 五、实现思路（分阶段）

### 阶段 0 · 数据迁移（幂等，可回退）

本项目**没有 Alembic**（`db.py:44` 只有 `create_all`），`create_all` **不会**给已有表加列。所以需要一段极简迁移：

```
1. 建新表            create_all 已能自动完成
2. 加 is_global 列   PRAGMA table_info 判断 → 不存在则 ALTER TABLE ADD COLUMN is_global BOOLEAN DEFAULT 0
3. 回填关联          INSERT OR IGNORE INTO template_projects SELECT id, project_id
                     FROM export_templates WHERE project_id IS NOT NULL
```

三条都可重复执行（幂等）。回退方式：不建表不加列即为旧行为，**不搬任何文件、不改任何观测数据**。

### 阶段 1 · 后端模型与服务

| 文件                                    | 改什么                                                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `models/export_template.py`           | 新增 `is_global`；`project_id` 标 **deprecated**（保留，不删）                                                                                 |
| `models/export_template_link.py`（新）   | `ExportTemplateProject` 关联模型                                                                                                        |
| `services/export_template_service.py` | `list_templates()` 改为「内置 + 通用 + 绑到本项目的」；新增 `set_template_projects()`；`create_uploaded_template()` 增加 `project_ids` / `is_global` 参数 |
| 文件落盘                                  | 新模板存 `templates/_library/{template_id}/`；**老文件原地不动**                                                                                |

**为什么老文件不搬**：

1. `file_path` 存的是绝对路径，搬迁会有断链风险；
2. 沙箱的"安全删除"守卫会拦截批量删除/移动，搬迁属于高风险动作；
3. 不搬 = 零风险，代价只是目录里有历史遗留，不影响功能。

**一个实现细节**：新模板要先进库拿到 `id` 才能定目录 → 顺序必须是 `db.flush()` 拿 id → 写文件 → `db.commit()`。

### 阶段 2 · API

| 接口                                             | 处理                                        |
| ---------------------------------------------- | ----------------------------------------- |
| `POST /export-templates/upload`（新）             | 上传到模板库，body 带 `project_ids` / `is_global` |
| `GET /export-templates`（新）                     | 模板库全量清单（带绑定项目），给"管理视角"用                   |
| `PUT /export-templates/{id}/projects`（新）       | 设置适用范围                                    |
| `GET /projects/{pid}/export-templates`         | **保留**，内部改按新规则筛选（导出页下拉继续用它）               |
| `POST /projects/{pid}/export-templates/upload` | **保留为兼容薄壳**，转调新接口并自动绑定 pid                |
| `GET /projects/{pid}/reports/excel`            | **补上归属校验**：模板非内置时必须「通用 or 绑定了本项目」         |
| `DELETE`                                       | 归属校验改为"模板存在即可"，并在删除时一并清关联                 |

保留兼容壳的好处很实在：**4 个既有测试文件基本不用改**（`test_export_template.py` 17 处、`test_hard_delete_template.py` 2 处、`test_master_report.py` 2 处、`test_control_values.py` 1 处），前端也能渐进迁移 —— 回归面小一个数量级。

### 阶段 3 · 删除语义调整

`hard_delete_service.py:107` 现在是**硬删项目 → 连带删光它的模板**。独立化之后必须改：

- 只删「**仅绑定这一个项目**」的模板
- 被其他项目共用的 → **保留记录，只解除本项目的关联**
- 提示语要说清：「这份母版还被 N 个项目用着，只解除本项目的关联」

### 阶段 4 · 前端

| 位置    | 改动                                    |
| ----- | ------------------------------------- |
| 上传弹窗  | 增加「适用项目」多选（**默认勾当前项目**）+「所有项目通用」开关    |
| 模板下拉框 | 只列「通用 + 本项目绑定」，分组标注「通用母版 / 来自 XX 项目」  |
| 模板旁操作 | 除已有的「重命名」外，再加「设置适用项目」                 |
| 防呆    | 取消勾选"当前项目"时二次确认（否则下拉里这份模板会当场消失，像丢了一样） |

**关于要不要新开一个独立「母版库」页 —— 建议放二期**。一期在导出页原地扩展，用户心智和操作路径都不变；独立页面要重做导航 + 列表 + 上传 + 绑定，改动量大，而当下收益（少传几次）在导出页就能拿到。

### 阶段 5 · 测试与守卫

- 新增 `tests/test_template_library.py`：跨项目共用、通用模板可见性、解绑后不可见、**导出归属校验**（不绑定的项目不能导）、迁移幂等、硬删不误删共用模板、误用他项目模板被拦
- 既有 4 个测试文件走兼容壳，预期只需少量调整
- 能力标记 `template_library` 同时登记进 `backend/main.py` 的 `BACKEND_FEATURES` 与 `frontend/src/App.tsx` 的 `REQUIRED_BACKEND_FEATURES`（有守卫 `test_capability_alignment.py` 盯着，漏一边会每次启动都弹"后端是旧版本"）

| # | 风险                 | 等级    | 说明与缓解                                                                                                                 |
| - | ------------------ | ----- | --------------------------------------------------------------------------------------------------------------------- |

## 九、需要你拍板的三件事

**1. 适用范围怎么表达？**  
推荐**多对多 + 通用开关**（方案 A）。如果你想更简单，也可以只做「全局 / 仅本项目」二选一 —— 少一个关联表，但"这份给 9 个项目中的 3 个用"就表达不了。

**2. 母版里的固定文字（概况/分析/结论段）怎么办？** ← 这是唯一代码解决不了的问题

- (a) **先加提示**：导出前提示"母版固定文字来自 XX 项目，请核对结论段"，你手动改 —— 改动最小
- (b) **做文本块覆盖**：每个项目可覆盖母版里的指定文字块 —— 一次性做对，但工作量约等于本次改造本身
- (c) **暂不处理**：接受现状（共用后问题更明显）

**3. 项目内上传入口要不要保留？**  
推荐**保留**（路径不变，内部转调），前端和 4 个测试文件几乎不用改；也可以顺手改成"项目页只能选，不能传，传都得去母版库"，形式更干净但回归面更大。
